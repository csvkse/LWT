# LXC 管理插件实机验证与优化方案

## 结论与当前状态

真实创建、CPU/内存/磁盘限制和网络行为均可在独占、可丢弃的 Linux 虚拟机或测试主机上验证。当前没有完成实机验证：此前只读探测的目标宿主未发现 Incus、LXC 或 PVE；本机隔离 Linux 容器没有 Incus 且 cgroup 只读。上述是此前观测，并非本次对所有潜在主机的重新扫描。不要在现有生产宿主自动安装 Incus、调整防火墙、创建网桥或挂载管理 socket。

已有 `plugins/lxc-manager/internal/incus/real_integration_test.go` 提供显式开启的真实 Incus 单实例创建、配置读取、启动、停止和清理测试；运行方法见插件 README。它直接测试 Incus 适配器，不经过生产 HTTP 创建预检，也不证明资源限制或网络实际生效。真实测试目前未运行。生产入口仍传入空的 `PreflightEvidence`，因此创建继续拒绝；`SampleResources` 是瞬时采样，不是容量预留或硬配额证明。

2026-11-07 对 Dev 部署主机只读检查显示它运行 Debian 12，同时承载 LWT 正式和开发容器，且未发现 Incus 客户端或默认 socket。该主机不是独占测试环境，因此不在其上安装 Incus 或初始化存储/网络。Incus 官方目前列出 Debian 12 的受支持包来自 Zabbly 仓库；添加仓库和安装服务须在独占测试 VM 上单独审查，不能由 manifest 命令隐式完成。

## 关键问题

1. **容器不等于完整虚拟机**：首期创建的是共享宿主内核的非特权系统容器；需要独立内核或强隔离的用户应另选 VM，不能在界面将二者混称。
2. **CPU 语义**：当前 `limits.cpu` 控制可使用的 CPU 集合或数量，不等价于保证 CPU 时间；如果产品要提供硬时间配额，需另行设计 `limits.cpu.allowance` 并验证调度行为。见 [Incus 实例配置](https://linuxcontainers.org/incus/docs/main/reference/instance_options/)。
3. **硬配额依赖存储后端和配置**：不能凭池名或驱动名给 `QuotaVerifiedForPool` 赋值。Incus 指出 Btrfs qgroup 有可绕过场景；`dir` 后端依赖底层 ext4/XFS project quota。参见 [Btrfs 限制](https://linuxcontainers.org/incus/docs/main/reference/storage_btrfs/)和 [存储驱动](https://linuxcontainers.org/incus/docs/main/reference/storage_drivers/)。
4. **容量检查存在竞态**：剩余空间、内存和 CPU 样本随时变化；并发请求若只检查一次，会超卖。必须在同一管理域内事务化预留，并考虑外部管理员及其他工作负载；无法覆盖的资源竞争须明确留出安全余量，不能声称硬保证。
5. **网络语义**：受管 bridge 可提供 DHCP、DNS 和 NAT，但路由、转发、防火墙和其他 bridge 间访问仍需在目标拓扑实测；NAT 不自动构成租户隔离。参见 [Incus bridge](https://linuxcontainers.org/incus/docs/main/reference/network_bridge/)。

## 实机准备与操作边界

使用专用 Linux VM，具有可用的 user namespace、cgroup 控制器、独立测试存储和测试网络，记录发行版、内核、Incus 版本、存储驱动、文件系统、挂载选项、cgroup 模式、镜像指纹和资源上限。预先准备专用测试池、受管网桥和本地可信镜像；这些准备会改变测试机的存储与网络，应仅在明确指定的可丢弃环境中进行。测试日志不得含管理凭据、真实业务地址或令牌。

先执行 README 中的 `TestRealIncusLifecycle`。其清理前检查名称、所有权、停止状态与快照，但检查和删除并非原子操作，测试机不得有其他管理者并发操作测试实例。异常中断后按测试日志人工核查残留。不得把该直接适配器测试通过当成插件端到端创建通过。

## 测试矩阵与判定

| 项目 | 实测方法 | 通过条件与记录 |
|---|---|---|
| 生命周期 | 执行现有真实测试；再经插件平台验证认证、预检、创建、重启后的任务核对与停止 | 后端实际状态与界面一致；记录异步操作 ID、阶段耗时和失败原因。端到端测试须待可信证据源实现后进行 |
| CPU | 测试容器运行固定时长的 CPU 负载，采集 cpuset、cgroup CPU 使用量及宿主基线；若实现时间配额，再测单核和多核竞争 | 可见 CPU 集合与设置一致；时间配额按其配置语义判定，记录测量窗口和误差 |
| 内存 | 在测试容器内逐步分配并触碰内存，观察 cgroup `memory.current`、`memory.max` 和 `memory.events`，包含 swap 配置 | 上限与配置一致，超过限制时发生可解释的限制或 OOM；记录进程退出和宿主压力 |
| 磁盘 | 专用小容量池与独立容器内逐步写入不可压缩数据直到失败；记录写入量、错误码、实际使用量、快照及删除后的回收 | 接近配置上限时可靠拒绝写入，宿主测试池不耗尽；对稀疏文件、快照、重启和后端已知绕过场景分别验证。一次正常写满不能证明恶意工作负载不可绕过 |
| 网络 | 测试实例获取地址并检查 DHCP/DNS；测试容器到宿主、容器间及外网；对专用测试端口测 TCP/UDP 入站、冲突、释放和 hairpin | 与事先声明的拓扑和隔离策略一致；记录地址、路由、连接结果、丢包及防火墙状态的脱敏摘要 |
| 并发与恢复 | 在固定资源预算下做 1、5、10 个并发创建，注入超时、进程中断和重复幂等请求 | 不重复创建或误删他人资源；预留不超卖；重启后能核对并释放已终结任务。记录 P50/P95、失败率和宿主 CPU、内存、磁盘 I/O |

磁盘写满、内存压力、网络规则和进程中断均有影响测试宿主的风险，须限制测试池、资源和运行时间，并设置人工停止条件。测试结束后核对实例、卷、快照、网络、进程和任务；只清理本次测试明确拥有的资源。保留原始脱敏数据和环境指纹，不预先编造性能阈值。

## 2026-11-07 Dev 实例验证记录

- Dev 应用已部署并通过健康检查；正式 `linuxwebtool` 容器未重建。
- 浏览器安装向导识别宿主发行版为 Debian，并默认选择宿主目标；通过宿主终端执行只读 `grep '^ID=' /etc/os-release`，实际返回 `ID=debian`。该检查确认宿主目标路由可用。
- 当前宿主仍无 Incus 客户端或默认 socket，且与正式服务共用；未安装 Incus、未增加仓库、未初始化存储池/网络。因此真实实例创建、资源硬限制、网络隔离和并发恢复尚未验证，不能将 Dev 部署或只读宿主命令视为这些能力的验收。

## 方案与设计模式

- **适配器**：继续由 Incus 适配器封装发现、实例和异步任务；PVE、LXD 保持独立适配器及能力矩阵，避免假设 API、权限和存储语义相同。[Incus REST API](https://github.com/lxc/incus/blob/main/doc/rest-api.md) 提供扩展发现、异步操作和事件；[官方 Go 客户端](https://github.com/lxc/incus/tree/main/client) 可评估，但应先核对版本、依赖、目标架构及并发行为，现有 Go 模块目前未依赖它。
- **策略**：为容量、CPU 限制、存储配额和网络策略建立按后端/池选择的实现；证据包含宿主、池、驱动、配置指纹、版本、采集时间和有效期，配置变化、后端重启或验证过期时失效。证据必须来自受信任服务端，不由浏览器传入。测试通过只证明特定配置和负载范围，不构成所有情况的数学证明。
- **状态机与协调器**：沿用持久任务和后端操作 ID，区分待预留、创建中、启动中、就绪、失败和需人工核对；对不确定结果先查询实际后端，禁止盲目重试或补偿删除。预留与释放必须原子化，单机文件锁不能解决多节点或外部管理者竞争。
- **性能**：优先复用后端批量查询和操作事件，限制并发并记录阶段耗时；按实际资源和负载确定并发上限。事件断线后需回查，不能把事件作为唯一状态源。

## 现有基础与业界参考

当前仓库已具备 Go 标准库 Unix socket HTTP 客户端、资源发现与采样、持久任务、Linux 跨进程锁、幂等处理、模拟后端测试、隔离实机生命周期测试和插件管理认证链；无需为首轮验证新增第三方库。当前 `PreflightEvidence` 仅是数据结构，尚无能证明容量预留和选定池硬配额的生产证据提供者。

Incus 提供系统容器、管理 API、存储和受管网络，适合作为当前首期后端。LXD 也提供存储驱动和配额能力，具体适用性按其版本和驱动验证：[LXD 存储驱动](https://documentation.ubuntu.com/lxd/latest/reference/storage_drivers/)。Proxmox VE 使用独立的容器管理和存储模型，适合已有 PVE 的环境，需要独立权限和 API 适配：[PVE 容器管理](https://pve.proxmox.com/pve-docs/pct.1.html)。项目级资源限制可作为补充约束，但不替代宿主容量预留和池级硬配额验证：[Incus 项目限制](https://linuxcontainers.org/incus/docs/main/reference/projects/)。

## 执行顺序与放行条件

1. 指定独占测试 VM，完成只读能力清单；确认存储、网络和回滚方式。
2. 在该 VM 准备专用 Incus 测试环境，先运行现有生命周期测试并记录结果。
3. 增加受限资源、网络和故障注入测试，先记录基线；任何证据缺失继续拒绝创建。
4. 实现服务端证据提供者与原子预留，补充并发、过期、配置变化和外部资源竞争测试，再执行插件端到端测试。
5. 按目标正式宿主重新验证环境与权限，确认 socket 暴露、审计和回滚，再决定是否启用；测试机通过不自动授权生产启用。
