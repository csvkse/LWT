# tmux 备用终端方案

记录日期：2026-10-02。状态：备用设计，不纳入当前实施计划。

## 当前决策

当前需求只要求软件运行期间，终端与浏览器页面解耦。Linux 使用原生 PTY，Windows 使用 ConPTY；应用内会话管理器持有进程、持续读取输出并提供有限回放。因此当前后台会话不依赖 tmux，也不需要独立终端宿主。

本文件保留此前 tmux 方案供未来评估，不意味着启用它。当前源码已移除 Docker 预装、后端检测与安装逻辑、安装 API 和前端入口，并同步相关测试、验证脚本与 README。已有镜像不会自动变化，需要重新构建后生效；不卸载用户主机自行安装的工具。

## 何时考虑启用

仅在未来明确增加以下需求时重新评估：

- Linux 会话需要同时通过 Web 页面与本机终端或 SSH 访问。
- 需要由应用外的终端多路复用服务统一管理会话、窗口与分屏。
- 需要会话独立于 Web 进程存活，并愿意额外定义部署、权限与宿主生命周期。

仅为浏览器刷新、关闭或网络断线续跑，不需要启用此方案。

## 备用接入设计

tmux 使用服务端进程管理会话，客户端可分离后重新附着。[官方介绍](https://github.com/tmux/tmux/wiki/Getting-Started)

以下为项目接入设计，尚未实现：

1. 保留当前原生 PTY 为默认后端；由明确配置选择 tmux 后端，缺少工具时反馈原因，不静默替换已运行会话。
2. 使用独立 socket 与受控会话标识隔离项目会话；执行参数通过参数数组传递，不拼接用户输入到 shell 命令。
3. 创建 tmux 会话时传入已验证的工作目录；Web 端通过原生 PTY 启动 tmux 客户端附着。浏览器断开只分离连接；显式结束只终止对应会话，不影响用户其他 tmux 会话。
4. 列表与退出状态以 tmux 实际会话为准；应用会话标识映射到受控 tmux 会话。继续实行访问权限检查与单输入控制者规则。
5. 区分“未使用 shell”与正在运行的任务；后台清理必须检查实际会话、任务状态，不能只检查附着客户端进程。
6. 重新验证目录报告、控制序列转发、全屏重绘、中文、窗口尺寸、Ctrl-C 和输出回放。现有 PTY 后端的验收不能直接证明 tmux 后端可用。

## 部署边界

| 环境 | 备用方案边界 |
|---|---|
| Linux 主机 | 通过发行版包管理器安装；socket 限制访问身份，Web 进程以受控用户访问 |
| Docker | 如选择该后端，在镜像构建时安装；容器停止会终止其中的 tmux 服务与会话，挂载数据卷不能保存运行进程 |
| Windows | 当前继续使用 ConPTY；WSL 内的 tmux 属于 Linux 环境，不能直接作为现有 Windows PowerShell 会话后端 |

即使未来要求跨 Web 软件重启存活，也必须保证 tmux 服务和 shell 不随 Web 进程退出而被终止。机器重启、宿主停止或 tmux 服务终止后的运行进程恢复不属于本设计能力。

## 启用前验收

- 浏览器断线后任务持续运行，重新连接仍是原 shell PID。
- 本机或 SSH 接入与 Web 控制者规则一致，不造成重复输入或权限绕过。
- 目录联动、中文、全屏程序、尺寸调整和 Ctrl-C 正常。
- 显式结束与自动清理仅影响项目自己的目标会话。
- 缺少 tmux、无 socket 权限或服务退出时，页面明确反馈真实状态。
- 若另行要求跨 Web 重启存活，必须按实际部署方式验证进程生命周期；安装成功不等于该能力可用。

以上为未来启用的验证清单，本次只记录文档，不安装或启用 tmux 后端。
