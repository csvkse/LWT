# 浏览器同时打开多个标签时的代理卡顿调查

## 结论与证据边界

目前不能确定用户实际卡顿的根因：尚缺实际目标网站、浏览器网络瀑布图及同一时刻代理阶段指标。此前在隔离开发环境对本地应用做了 1/5/20 标签各三次对照，234 次导航成功；20 标签页面 load p50 为直连 1110.9 ms、HTTP 代理 1114.2 ms、SOCKS5 代理 1049.2 ms。单标签约有 13 ms 的代理差距。这只是本地页面、小样本的结果，不覆盖公网 DNS、跨网路由、网站反爬、真实缓存状态和突发资源分布。另有 50/100/500 连接阶梯及 500 路双向五分钟 soak，但 echo 隧道不能代表网页加载。详见 [容量实测](socks5-proxy-capacity-ladder-and-runtime-observability-design.md#9-本轮执行记录2026-11-05)。

## 多标签同时打开时的可能原因

| 优先观察 | 机制与可验证证据 | 当前判断 |
|---|---|---|
| 同时新建连接和往返 | 每个新隧道都要连接代理、协商 SOCKS5 或 CONNECT，代理再解析并拨号；HTTPS 还需浏览器与目标协商 TLS。突发时多个站点的慢阶段会叠加。 | 协议必然有额外路径；实际占比未测。 |
| 冷 DNS 与出口位置 | SOCKS 域名请求由代理端解析；代理和本机解析器或 CDN 选址不同，同域名冷缓存请求需要等待首次解析。 | `dns_cache.go` 已有缓存、singleflight、stale 和负缓存；需测冷/热差异与解析结果。 |
| IPv4 路径与拨号竞速 | 当前先查 IPv4；有 A 记录即不返回 IPv6，只有 IPv4 无结果才回退双栈。拨号最多前四个候选，按 120 ms 阶梯启动。IPv4 不佳或前几个 CDN 地址慢时可能增加尾延迟。 | 是有证据的实现特性，不等于已证实是本次根因；现有实现不能视为完整双栈 Happy Eyeballs。 |
| 浏览器请求队列 | 同时加载大量资源会受请求优先级、连接复用、HTTP 版本和缓存影响；Chrome 将 Queueing、Stalled、Proxy negotiation、DNS、连接和 TTFB 分开显示。 | 采集各请求 Timing 与协商协议后判断；不要把 Stalled 全部归因代理。 |
| 代理和目标资源 | 全局 session 默认 512；不足时会拒绝。普通 HTTP forward 有每目标 active/pending 限制，CONNECT 和 SOCKS tunnel 走各自隧道路径，不能将 forward 的连接池参数当作所有 HTTPS 的优化开关。目标网站、代理宿主 CPU/FD、网络丢包也可能成为瓶颈。 | 检查 `activeConns`、`rejectedConns`、HTTP pending/timeout 和系统资源的增量，再与浏览器时间线对齐。 |
| HTTP/3 与协议差异 | SOCKS5 TCP CONNECT 路径没有提供 UDP ASSOCIATE 的证据；走代理后网站可能采用不同传输协议、连接复用或 CDN 路径。 | 从浏览器 Network 的 Protocol 和连接记录核实，不能假定所有代理场景均降级。 |

Chrome 官方对 Timing 阶段的定义和 HTTP/1.x 每源连接排队说明见 [DevTools Network reference](https://developer.chrome.com/docs/devtools/network/reference)。排队也可能由浏览器优先级和磁盘缓存引起；不要把六连接限制推广到 HTTP/2 或所有代理连接。

## 首轮同步开标签基线（2026-11-05）

运行现有 `tests/benchmark/proxy-multitab-performance.mjs`，同一 Chromium 启动后通过 `Promise.all` 同时导航所有标签；3 样本，direct、HTTP proxy、SOCKS5 proxy，标签数 1/5/20。受控开发页面每页约 21 个请求，27 个组合全部成功、页面请求失败为 0。20 标签页面 load p50：direct 1,038.9 ms、HTTP 1,016.7 ms、SOCKS5 1,139.5 ms；批次 wall p50 分别 1,287.9、1,185.6、1,392.4 ms。5 标签下 SOCKS5 页面 load p50 为 480.5 ms，HTTP 377 ms，direct 418.4 ms。这里 SOCKS5 相对 HTTP 的差距在 5/20 标签可见，但本机目标是 IP 地址，DNS cache、远端解析和公网路由没有参与；尚未采集服务器阶段指标。

同日对 `https://example.com/` 做相同 3 样本实验，每页仅约 2 个请求，全部 234 次导航成功。20 标签页面 load p50：direct 2,372.3 ms、HTTP 2,698.7 ms、SOCKS5 2,720.0 ms；批次 wall p50 分别 2,480.2、4,796.6、4,699.2 ms；导航 TTFB p50 分别 2,165.9、595.1、588.1 ms。5 标签时 HTTP/SOCKS 页面 load p50 分别 1,239.8/1,261.7 ms，TTFB 为 601.6/619.5 ms。两种代理结果接近，且代理 TTFB 显著低于直连而总 load 较长；这更像浏览器等待页面后续资源/外部路径或测量顺序差异，不能指向 SOCKS5 协议实现。该公开站点样本少、模式按 direct→HTTP→SOCKS 顺序执行，外部网络随时间变化，结果只作线索，不作为优化前后对比或性能门禁。

**本轮定位结论：** 同步多标签的受控测试没有失败或代理准入拒绝证据；5/20 标签本地 SOCKS5 有约 100–120 ms 的页面 load 差距，但该页面不经过 DNS。公网样本中 HTTP 和 SOCKS5 近似，SOCKS5 没有可辨认的额外劣化。当前证据不足以安全改变 DNS、拨号竞速或连接复用策略，改动这些会影响 SSRF/ACL、CDN 选址和长连接语义。已经完成基线执行和证据归档；实际代理服务器 active/rejected、DNS/dial 阶段分位数及浏览器完整资源 waterfall 未与公网样本同步采集，因此不能宣称已定位并修复用户所遇卡顿。

下一轮比较应先把模式执行顺序轮换或随机化、增加暖机样本并保留每个请求的 Chromium/CDP timing，再同步采集代理状态快照；目标站点要按用户实际复现环境选取。仅当这些数据显示 DNS、TCP 拨号、代理握手或服务端排队中的某一阶段稳定占主导时，才做对应数据面优化并重复同一矩阵。

## 轮换顺序与请求阶段复测（2026-11-05）

测试脚本已改为每轮轮换 direct、HTTP、SOCKS 的执行顺序，使用 Chromium CDP 收集可用的代理协商、DNS、连接和发送后等待响应头时间；缺失阶段以样本数 0 和 null 表示，不当作 0 ms。统计只保存耗时和样本数，不记录 URL 或头部。新增测试覆盖模式轮换与缺失阶段处理。

对 `https://example.com/` 同时打开 20 标签，三轮轮换顺序，三种模式各 60/60 导航成功。批次 wall p50：direct 2,368 ms、HTTP 951 ms、SOCKS5 901 ms；页面 load p95：direct 2,343 ms、HTTP 922 ms、SOCKS5 835 ms。CDP 代理协商计时在三种模式均无有效样本；HTTP/SOCKS 连接阶段各仅 3 个有效样本，不能将其当成每个请求的独立连接。发送后等待响应头 p95 分别为 2,161、685、607 ms。该指标不覆盖浏览器排队，连接计时可能包含 TLS，不能单独归因代理。

上一轮同站点代理批次 wall p50 约 4.7–4.8 秒，本轮约 0.9 秒，显示环境波动和测试顺序对结果影响很大；两轮测试方法不同，不能作为代理性能改进的前后对照。本次改动改善了测量顺序与缺失值处理，未修改代理数据面，也尚未证明用户真实站点的卡顿原因。仍需同步代理端状态与用户实际目标的脱敏网络时间线后，再进行针对性优化与同条件复测。

## 同步浏览器与代理端采样（2026-11-05）

浏览器脚本新增可选 `MULTITAB_TRACE_FILE`，按模式、轮次和标签记录浏览器启动、导航窗口及 CDP 响应事件时间、协议、状态和可用阶段耗时，不保存 URL、请求头或凭据。Linux 开发容器运行采样器，每 250 ms 采集 status、runtime、DNS 命中和拨号累计值、FD/RSS 及 cgroup。浏览器与服务器时钟经往返估算相差约 1.3 秒，误差约半秒；短请求不能靠这次时钟校准精确对应单条连接。代理 status 是进程级累计值，且开发实例由多个连接共享，无法按浏览器请求归因。

对 `example.com` 的 20 标签三轮同步采样，三种模式各 60/60 导航成功，页面 load 前观察到的失败请求总数为 0。批次 wall p50：直连 2,356 ms、HTTP 917 ms、SOCKS5 919 ms；所有被观察到的 Document/Script 响应均为 HTTP/2，三轮各模式仅有 3 个可用连接计时样本，表明不能把标签数直接当作新建 TCP 连接数。代理协商阶段的 CDP 计时无有效样本。该站点仅约两个请求/页，不代表复杂网站。

采样起始代理已有 7 个活动会话，期间采样峰值 36，FD 峰值 130；拒绝数始终 0，cgroup CPU throttling 与 OOM 增量均为 0。某次直连浏览器窗口内，代理同时完成 7 次上游拨号，累计耗时约 70 秒，均值约 10 秒；这些拨号属于共享代理，无法确认与本轮浏览器窗口的任何请求相关。采样结束后再次读取 status，活动会话回到 7。当前证据不支持会话上限、FD 或 CPU quota 是该次样本的瓶颈，也不能证明上述慢拨号就是用户卡顿根因。

本轮修正测试门禁：此前只以主文档失败判定非零退出，少数资源失败可能被每页失败数中位数掩盖；现在任何在 load 事件前观察到的 `requestfailed` 都使测试失败，并输出失败总数。回归测试覆盖单个资源失败与时间线脱敏，相关 10 项 Node 测试通过；公网同步复测失败总数为 0。load 事件之后的异步请求仍需另设观察窗口才能覆盖。

这些改动改善的是采样和测试门禁；没有对代理数据面做优化，也没有取得代理性能优化前后对照。下一步需在隔离的代理实例上用受控慢 DNS/黑洞上游复现约 10 秒拨号，并通过低基数逐阶段完成/失败计数或脱敏关联 ID 将浏览器请求与代理拨号对应；再结合用户实际卡顿目标，先证明慢阶段，再实施并以同一 workload 复测。不能仅凭共享实例的累计计数调整超时、重试或会话上限。

## 用户提供的公开视频页面：同步定位与节点对照（2026-11-05）

用户提供的视频页面去除跟踪参数后进行了实测。一次 5 标签对照中，直连 5/5 页在约 3.6 秒内完成 load；开发容器 HTTP 与 SOCKS5 代理各 0/5 在 30 秒内完成 load。一次 20 标签对照中，直连 20/20 完成，HTTP 0/20、SOCKS5 1/20 在 30 秒内完成；资源失败分别为直连 1、HTTP 32、SOCKS5 46。网站资源、广告和网络状态会变化，这些是单次复现，不是稳定 SLA。

在另一次 5 标签采样中，五个标签的主文档均获得 200；有有效首屏时间的标签中，直连首个内容绘制中位数约 2.64 秒，HTTP 代理约 27.93 秒，SOCKS5 在 30 秒窗口内没有采集到有效首个内容绘制或 DOM 完成时间。该轮尚未报告首屏有效样本数，因此不能将中位数推广到全部五个标签；脚本现已补充有效样本数。CDP 按临时随机 HMAC 对来源分组发现，大量未完成 Script 集中在同一个静态资源来源；只保存标识和时间线，原始来源/资源路径仅在显式指定临时映射文件时写入本机，不保存查询参数或凭据。此类文件可能含敏感路径，应限制访问并在排查结束后由操作者删除，不提交到仓库。

开发代理同步采样共 671 个样本，活动会话起止均为 5、峰值 29，拒绝增量为 0，未观察到 cgroup throttling/OOM。20 标签 SOCKS 窗口中 DNS 58 次累计约 0.25 ms，57 次上游拨号累计约 110 秒；这些值是所有并发请求耗时的总和，不能当作单次延迟或精确归属某一页面。HTTP/SOCKS 同时存在长尾，不能将问题归为 SOCKS 握手。浏览器目标文档及脚本多使用 HTTP/2；连接计时有效样本较少，不等同于请求数。

对其中一个约 4 MB 的公开脚本做受控对照：

| 对照 | 实际结果 | 解释 |
|---|---|---|
| 浏览器所在机器直连 | 约 2.46 秒接收完 4,042,153 字节 | 当前客户端出口的一次样本。 |
| 开发容器代理，HTTP / SOCKS5 | 20 秒分别接收约 0.61 / 0.65 MB，均超时 | 两种协议均慢。 |
| 开发容器直接访问同一资源 | 约 21 秒接收 0.75 MB | 无代理转发时也慢。 |
| 容器直连和隔离代理，强制访问代理实际选中的同一 IP | 一轮均在约 20 秒接收 0.7 MB；另一轮分别约 18.2 秒和 13.1 秒收完约 4 MB | 同一目标 IP 的网络/节点吞吐会波动；本实验未证明代理 relay 是主要瓶颈。 |
| 同一隔离代理、相同 TLS SNI 与 Host，显式选择另外两个候选 IP | 两次均约 2.2 秒收完约 4 MB；同期按域名解析路径约 20.8 秒仅收 0.71 MB | 节点选择在这次实验中影响显著；这些地址并非稳定推荐值。 |

宿主与容器一次 DNS 采样返回不同地址集合；同一批固定 IP 分别从宿主和容器访问时均可在约 2.8–5.8 秒完成，不能据此断定 Docker 网络本身一定慢。多次解析返回的 CDN 地址发生变化，随后新结果也不总包含之前的快节点；仅降低 DNS 缓存 TTL、固定某个地址或以 TCP 握手最快作为吞吐保证均缺少充分证据。TLS 隧道建立后无法无损切换到其他节点，不能自动重放加密请求。

### 自定义 DNS 和按域名分流的可行方案

已测到的直接现象是部分候选 CDN 地址的**数据传输速率低**：同一地址从容器直接访问和通过隔离代理访问都慢，另两个候选地址通过同一代理可快得多。DNS 解析耗时、连接建立耗时、传输吞吐和 TCP 丢包是不同指标；本轮没有测量重传或丢包率，也没有证明 DNS 查询本身普遍慢。DNS 返回的地址会影响后续选路，但也可能受出口路由、CDN 节点负载和运营商链路影响；更换 DNS 不保证得到快节点。

现有代码的 `IDnsResolverStrategy`、`CachedDnsResolver` 和拨号前逐 IP ACL 检查已被复用；`Ipv4PreferResolver` 使用 Go `net.Resolver`，默认依据运行环境的解析配置。本轮新增可选 `SOCKS5_DNS_RULES` 环境变量，支持指定 DNS 上游和域名分流。Go 的 [Resolver.Dial](https://pkg.go.dev/net#Resolver) 支持指定 DNS 服务连接，CoreDNS 的 [按域名转发方案](https://coredns.io/manual/setups/)可作为行为参考。

实现边界与后续扩展：

1. 规则按最长后缀匹配；例如 `video.example.com` 和子域匹配专用 DNS，其他域走默认 DNS 或 `*` 规则。区分标签边界，避免 `notexample.com` 命中 `example.com`；支持大小写与末尾点归一化，国际化域名须提前转成 ASCII punycode，不接受原始 Unicode。
2. 每条规则绑定独立的上游地址和传输策略。第一阶段支持配置 IP 字面量加端口的传统 DNS，正确处理 UDP 与 TCP；按需后续扩展 DoT/DoH、证书校验和 bootstrap。不要依赖要通过自身解析的 DNS 主机名启动自身，避免循环。未配置时保持现有系统 DNS 行为。
3. 每条规则使用独立缓存和 singleflight，避免不同 DNS 视图混用。当前规则只在进程启动时读取，需重启插件生效；正缓存软/硬 TTL 可按规则设置，负缓存 5 秒。指定上游失败时不回退默认 DNS，避免域名意外发往其他解析器；热更新和可选回退仍需后续单独设计。
4. 所有 DNS 返回的候选 IP 在拨号前仍必须经过现有 ACL、防 DNS rebinding 与连接上限；显式 IP 请求也不能绕过目标 IP ACL。DNS 端点必须限制为管理员允许的地址，禁止不受信任用户指定任意上游。不要自动写死本轮实验获得的 CDN IP。
5. 状态接口报告规则数与合计缓存统计，不记录完整域名、路径或 DNS 上游。单元测试覆盖最长后缀、缓存、UDP 截断切 TCP、配置校验、默认失败不回退及 IP ACL。每规则独立指标、热更新、DoT/DoH、DNSSEC 与用户界面尚未实现；仍需扩大取消、重载与真实网络回归。

`SOCKS5_DNS_RULES` 环境变量的 JSON 数组示例：

```json
[
  { "suffix": "video.example.com", "server": "198.51.100.53:53", "softTtl": "30s", "hardTtl": "1m" },
  { "suffix": "*", "server": "192.0.2.53:53" }
]
```

示例地址为文档保留地址，不能作为可用 DNS；`127.0.0.1` 在容器里指容器本身。不同出口不属于这项功能的前置条件：可以先在同一出口比较多个授权 DNS 返回的地址与实际吞吐。DNS 分流与浏览器按域名直连分流是两种不同的功能；前者仍通过原有代理转发。

可在需要比较的出口运行以下命令；默认读取本机配置的 DNS 上游，每次只探测每个上游的前两个 IPv4 候选、两轮，每次最多下载 8 MiB、等待 12 秒。仅对有权访问的 HTTPS 静态资源运行：

```powershell
$env:DNS_BENCH_URL = 'https://example.com/asset.js'
$env:DNS_BENCH_REPEATS = '2'
$env:DNS_BENCH_CANDIDATES = '2'
node tests/benchmark/dns-cdn-compare.mjs
```

可选 `DNS_BENCH_SERVERS` 为逗号分隔的 IP 字面量 DNS 上游；不设置时使用当前环境配置。输出只包含每次运行内随机标识的地址、TTL、字节、耗时、状态及完整响应的 SHA-256，不输出 DNS 地址或资源 URL。工具对公网目标拒绝私网/回环解析结果，固定 TLS SNI/Host；这是容器直接出站 HTTP/1.1 对照，不能替代浏览器 HTTP/2 或经过代理的端到端测试。

### DNS 可行性对照：改动前基线

现有代理使用运行环境默认 DNS、IPv4 优先、3 分钟软 TTL / 10 分钟硬 TTL，没有自定义 DNS 或分流入口。前述同资源实验中，域名选中的慢节点 20 秒约 0.71 MB；显式选择两个不同候选节点，经同一隔离代理分别约 2.2 秒收到约 4 MB。该实验说明**候选地址选择可能有用**，并不证明某个 DNS 上游总能返回快节点，也不证明 DNS 查询本身慢或链路丢包高。后续对照在同一容器出口并发查询容器已配置 DNS，固定 TLS SNI/Host 与资源，分别测解析耗时、答案、逐地址完整传输速度和一致性；原始域名、IP 和资源路径不写入结果。`tests/benchmark/dns-cdn-compare.test.mjs` 使用两台本地虚拟 DNS 验证解析视图隔离和地址过滤。

### 真实浏览器 DNS 分流多标签验证（2026-11-05）

用本机 Chromium、同一 Bilibili 视频页面、同一网络和 5 个同时导航标签比较直连、HTTP 代理及 SOCKS5。所有隔离代理监听开发容器端口，只有临时 SOCKS5 实例使用自定义 DNS；共享开发代理和生产实例没有改配置。每个条件目前完成一轮，结果如下：

| 条件 | 页面成功 | load 中位 / p95 | TTFB 中位 | DOM ready 中位 | 首屏样本 | 失败请求 | 每页请求数中位 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 直连 | 5/5 | 3.29 / 3.30 秒 | 157 ms | 2.82 秒 | 5/5 | 0 | 34 |
| 默认 DNS SOCKS5（基线） | 5/5 | 4.74 / 4.87 秒 | 431 ms | 3.80 秒 | 5/5 | 0 | 29 |
| 分流 DNS SOCKS5 | 5/5 | 6.09 / 14.16 秒 | 749 ms | 5.25 秒 | 4/5 | 0 | 204 |
| HTTP 代理（上下文参照） | 5/5 | 9.94 / 9.96 秒 | 388 ms | 9.06 秒 | 5/5 | 0 | 28 |

另一次默认 SOCKS5 基线样本 load 中位为 4.65 秒，5/5 页面成功、0 个失败请求。由于该站点按会话动态加载资源，单轮间每页请求数从约 29/36 变为分流组 204；因此请求量和尾延迟不能归因于 DNS，也使这组 A/B 不满足严格同请求量对照。分流代理状态确认规则数 2、结束时 active 0；默认代理规则数 0、结束时 active 0。两组代理均有 DNS 缓存命中和未命中，分流组并未出现连接泄漏。每轮只有 5 页，不能据此推断 20 标签或稳定的整体改善。

浏览器阶段数据将差距定位在 DNS 之后：分流组 TTFB 和 DOM ready 比默认组更慢，页面完成时间长尾也更大；代理握手阶段没有可用浏览器侧单项计时。分流并未减少页面失败请求，但也没有缩短加载。此轮采用的上游与该 CDN 组合没有改善效果，所以不把它设为默认，也没有继续调整 TTL 或扩大域名范围。较高请求数提示网站动态资源/播放器初始化带来明显样本差异；要判断 CDN 地址选择效应，下一步需固定同一个静态资源页面或 HAR 请求集合，按交错顺序重复至少 3 轮，再同时对比目标 CDN 的 `connect`、TLS、TTFB 和下载阶段。不能把页面的动态请求数变化当成 DNS 的因果证据。

### DNS 分流实现与复测结果（2026-11-05）

在同一 Linux 容器内直接查询两个已有 DNS 上游、每个查询两轮，每轮各测两个 A 记录，并固定同一资源、TLS SNI 和 Host。上游 1 的解析耗时为 71–95 ms，4/4 个候选在 12 秒内未收完；上游 2 的解析耗时为 187–197 ms，4/4 个候选完整接收 4,042,153 字节，耗时 4.66–6.74 秒，内容 SHA-256 一致。DNS 慢一些不妨碍它在该次样本中返回吞吐更好的地址；A 记录答案和 CDN 状态会随时间变化。

新增的分流实现已在 `linuxwebtool-dev` 插件热更新；未配置规则的实例报告 `dnsRuleCount=0`，保持原系统 DNS。另启动两份仅监听容器回环地址的隔离代理，分别使用系统默认 DNS 和为静态资源域配置的上游 2（软 TTL 30 秒、硬 TTL 1 分钟）。每轮两组同时发起各 5 次 HTTPS CONNECT，校验完整内容和 SHA-256：

| 轮次 | 默认 DNS | 分流 DNS | 结果边界 |
|---|---|---|---|
| 首次两轮合计 | 10/10 完成，中位约 3.30 秒 | 10/10 完成，中位约 6.57 秒 | 所有完成文件哈希一致；默认解析在此时更快。 |
| 再测第一轮 | 5/5 完成，中位 2.54 秒 | 5/5 完成，中位 4.81 秒 | 默认缓存出现 5 次 stale hit 并触发后台刷新。 |
| 再测第二轮 | 0/5 在测试上限内完成 | 5/5 完成，中位 4.91 秒 | 默认组只有部分数据；分流组 5 次内容哈希一致。 |
| 可复跑工具两轮 | 10/10 完成，各轮中位 2.53、2.60 秒 | 10/10 完成，各轮中位 5.94、6.17 秒 | 规则数分别为 0 和 1，所有文件哈希一致；两轮结束 active 均为 0。 |

另外，SOCKS5 域名模式各取一次，默认和分流均完整下载且哈希一致，分别约 2.75 秒和 5.14 秒。Linux 隔离实例使用本地虚拟 DNS 返回 ACL 不允许的 IP 时，SOCKS5 实际返回规则拒绝码，确认分流未绕过 ACL。UDP 截断切换 TCP、最长后缀、无隐式回退、独立缓存、非法配置和 ACL 的自动化测试通过。`localhost` 在该 Linux 容器优先由 hosts 文件解析，专用 DNS 未收到查询；这是 Go 解析器遵循运行环境 hosts 顺序的限制。

结论：**自定义 DNS 与按域名分流可行，在某些解析批次可避免慢 CDN 地址，但本次并非持续比默认 DNS 快。** 默认 DNS 组也可短时间获得更快节点，刷新后又可能变慢；每组样本少且目标、网络和 CDN 均会变化。因而规则保持 opt-in，不为该站点自动固定 DNS 或 IP，不据此声称浏览器卡顿已普遍修复。以上 A/B 为 5 个并发 HTTP CONNECT 资源下载及单个 SOCKS5 资源，未对配置分流的代理完成真实浏览器多标签 A/B。Linux 服务镜像缺少 Go/GCC，本轮未覆盖当前源码的 Linux race detector。

本轮优化了测试工具的时间线、失效请求门禁和 load 超时后的首屏/DOM 测量，并增加约 4 MB TCP relay 完整性测试；本机 Go 测试及相关 Node 测试通过。新增可选 DNS 路由已进入代理拨号路径；**2.2 秒是隔离代理中的固定候选节点实验，不是默认配置的优化效果。** 后续应在专用隔离环境比较 DNS 策略，并使用稳定的合成慢/快节点验证候选策略的收益、恢复、ACL 和错误率；只有多轮 A/B 证明不会损伤正常站点后再考虑默认策略。不要把实验 IP 写入产品或在未确认安全策略时自动绕开代理。

可在两个已配置好的隔离代理所在机器，复跑 HTTP CONNECT 单资源并发对照；状态接口须分别位于代理端口加 1000，默认组规则数为 0、分流组规则数至少为 1：

```powershell
$env:DNS_AB_URL = 'https://example.com/asset.js'
$env:DNS_AB_DEFAULT_PORT = '28111'
$env:DNS_AB_SPLIT_PORT = '28112'
python tests/benchmark/dns_split_proxy_compare.py
```

默认每组同时 5 连接、运行两轮，目标应是有权访问且内容固定的 HTTPS 静态资源。输出不含 URL 或服务器地址；会报告状态采样、每次完成情况、耗时和内容哈希。任一下载不完整、哈希不一致、状态不可用或规则数不符合要求时门禁失败。设置 `DNS_AB_ALLOW_INCOMPLETE=1` 可在排障时保留不完整下载样本而不因其退出失败，但规则错误和已完成内容哈希不一致仍会失败。脚本不能替代浏览器多标签全页面测试。

最后一次 5 标签复测补充了指标的有效样本数：直连 5/5 完成，首屏 p50 为 2.78 秒；HTTP 代理 5/5 主文档成功但全部在 30 秒等待 load 超时，5/5 均有首屏数据，中位数 25.97 秒；SOCKS5 5/5 完成 load，首屏 p50 为 3.09 秒、load p50 为 4.26 秒。三组各只有一轮，依次执行；该结果体现同一环境下长尾的波动，不是代理代码优化带来的改善。同步采样中，HTTP 窗口 DNS stale hit 增量为 18，随后 SOCKS 窗口为 0、普通 hit 增量为 24；这些是共享进程所有目标的累计值，与缓存刷新和节点变化的时间关系相符，但无法证明造成差异的是哪一个域名或缓存刷新。

### 如何复跑同步测试

在已启动的隔离代理所在机器运行；将目标换成获得授权的页面：

```powershell
$env:WEB_BENCH_URL = 'https://example.com/'
$env:PROXY_URL = 'http://127.0.0.1:18080'
$env:SOCKS5_PROXY_URL = 'socks5://127.0.0.1:18080'
$env:MULTITAB_STATUS_URL = 'http://127.0.0.1:19080/api/status'
$env:MULTITAB_COUNTS = '5,20'
$env:MULTITAB_SAMPLES = '3'
$env:MULTITAB_TRACE_FILE = Join-Path $env:TEMP 'proxy-multitab-trace.json'
node tests/benchmark/proxy-multitab-performance.mjs
```

`MULTITAB_STATUS_URL` 仅接受本机回环地址；客户端与代理分机时，在代理所在容器运行 `proxy-capacity-sampler.py`，并校准两端时钟及采样误差。默认 trace 保存随机标识、时间和状态，不含主机名或路径。`MULTITAB_ORIGIN_MAP_FILE` 可选择性保存来源主机映射；`MULTITAB_RESOURCE_HOST` 与 `MULTITAB_RESOURCE_MAP_FILE` 同时设置时还会保存该主机脚本资源的无查询参数路径。这些映射仅用于本机排障，可能包含敏感标识，不应提交或直接分享。当前资源失败门禁覆盖批次结束前事件；load 后长时间异步请求需另设观察窗口。

## 已有能力与业界方案

- 本仓库 `tests/benchmark/proxy-multitab-performance.mjs` 已能比较 direct、HTTP 和 SOCKS5 的页面导航；`proxy-capacity-load.mjs` 能做真实 tunnel 数量、双向数据完整性和 drain 检查。应扩展突发启动与冷/热缓存采样，而非重新开发测试框架。
- `dns_cache.go` 有 LRU、singleflight 和 stale 机制；`dialer.go` 有候选 IP 竞速；`http_proxy.go` 的共享 `http.Transport` 已设置 `MaxIdleConns=128`、`MaxIdleConnsPerHost=16` 和每目标连接上限；`admission.go`、`http_admission.go` 提供有界准入和计数。`/api/status` 的 DNS/拨号只有 count/total/max，不能计算 p95/p99，也不能关联到单次导航。SOCKS5 模块 `go.mod` 没有第三方运行依赖。
- Go [net/http Transport](https://pkg.go.dev/net/http#Transport) 提供连接复用和 per-host 连接控制，适合现有普通 HTTP forward；HTTPS CONNECT 后由浏览器与目标通过 tunnel 复用，不能通过简单增大代理 Transport 池改善所有 HTTPS。
- [Go net/http/httptrace](https://pkg.go.dev/net/http/httptrace) 可观测 Go HTTP 客户端连接获取、DNS 和 TLS 阶段，适用于 forward 上游诊断；SOCKS/CONNECT 的代理握手和浏览器 TLS 仍需分别埋点与浏览器侧采集。
- [Envoy connection pooling](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/connection_pooling.html) 与 [pending request queueing](https://www.envoyproxy.io/docs/envoy/latest/configuration/upstream/cluster_manager/pending_request_queueing) 借鉴连接复用、有界等待和溢出观测。当前已有对应基础，迁移完整 sidecar 的复杂度不适合在定位前引入。
- [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/instrumentation/) 和 [Prometheus Go client](https://github.com/prometheus/client_golang) 可提供统一指标与直方图；`mcp-bridge` 的间接依赖不等于 SOCKS5 已有 exporter。先评估现有采集系统和标签成本，再决定是否引入；不要记录完整 URL、凭据或高基数域名。

## 具体定位与优化方案

1. 固定同一客户端、网络、浏览器版本和目标，采集直连、SOCKS5、HTTP CONNECT 三组；分别测试首次启动冷缓存、同会话热缓存。记录实际目标经脱敏的 HAR/NetLog、协议、重试和瀑布图；避免保存 Cookie、Authorization、URL 查询参数等敏感内容。优先复现真实卡顿，控制目标访问速率。
2. 用同步屏障同时打开 1/5/20 标签，再逐步提升至环境允许的数量；区分同域多标签、不同域多标签，固定每页资源数量与大小，并加入受控 DNS 慢响应、首个 IP 黑洞、慢 TLS/TTFB 的本地目标。每种条件至少三轮，交错运行直连与代理，记录 p50/p95/p99、失败率、卡顿超过阈值的比例和每轮资源曲线。阈值先由稳定基线和用户体验目标确定，避免把本地 13 ms 当成公网 SLA。
3. 通过现有 status 同步采集 active/peak/rejected、HTTP pending/timeout、DNS 命中和 DNS/dial count/total/max、goroutine、FD、RSS、cgroup throttle。增量仪表优先补有界直方图或采样阶段耗时：代理入站等待、认证/握手、DNS、各次拨号及总建连，按协议、结果等低基数字段统计。与浏览器时钟对齐；status 不应直接输出目标或用户标识。
4. 若冷 DNS 主导，先验证缓存合并与失败恢复，再比较代理 DNS 路由及 TTL；避免未经实测统一延长 TTL。若慢 IP/IPv4 路径主导，在独立策略适配器中原型化双栈候选和可配置竞速间隔，严格保留 ACL 对每个候选 IP 的检查、总超时、赢家之外连接关闭，并与现行策略做配对 A/B。若是会话拒绝或队列等待，结合 FD/内存和目标容量调整上限，不盲目放大。若浏览器自身排队或 TTFB 主导，先定位资源优先级、HTTP 协议和目标响应。
5. 仅当 profile 证明调度、锁或 GC 是瓶颈时再考虑 event loop；保留标准库 HTTP 取消、keep-alive、CONNECT 预读及半关闭语义。测试运行器可用协议适配器、idle/突发策略与明确的 ramp/steady/drain 状态；生产侧避免为单一策略引入状态机框架。

## 回归门禁

- 同步突发的同域/跨域 1/5/20 标签直连和两种代理均完成导航；统计失败、请求丢失、握手及页面 p50/p95/p99，与固定环境历史基线比较并保留原始脱敏结果。测试应覆盖真正同时启动，而不是逐标签串行打开。
- 慢 DNS 的同域并发只触发预期的合并查询；首次失败、取消、过期和 stale 刷新后可以恢复，不能错误缓存安全策略结果。
- 首个 IP 延迟/失败、双栈不对称、所有候选失败及 ACL 禁止候选时，验证总超时有界、禁用地址不被拨号、竞速输家关闭、客户端取消释放资源。
- 会话达到小型可配置上限时验证拒绝计数、恢复和 active 回零；HTTP forward 验证 pending 限额、排队超时、取消释放，SOCKS/CONNECT 分别覆盖握手首包、双向完整性、半关闭及 drain。
- 每轮结束后检查 active/pending、FD 和 goroutine 回落；采集 CPU、RSS、GC 和 cgroup throttling。补具备 Go、cgo 和 GCC 的 Linux race 检查；现有最新源码 race 未完成，不能标记为通过。
- 对照真实网站结果时按浏览器 Protocol、缓存状态和网络阶段分组；公开报告只保存脱敏信息，且不以单轮 localhost 测试证明公网卡顿已修复。
